## 1. 진행 원칙

1. **전투가 재미없으면 온라인을 만들지 않는다.** 단계 0 게이트 실패 시 다음 단계 착수 금지.
2. **온라인 신뢰성(원장·재접속)이 증명되기 전에는 콘텐츠를 대량 생산하지 않는다.**
3. 각 단계는 "질문 하나에 답하는 플레이 가능한 결과물"로 끝난다.
4. 수치는 측정값으로만 확정한다. 측정 전 문서 수치는 가설로 표기.
5. 구현 담당은 최신 사용자 결정과 yeonmu `CLAUDE.md`를 따른다. 2026-11-07 단계 0은 Codex Astra 구현·Claude 코디네이터 점검으로 변경됐다. 기존 기획 교차 검토 결과를 유지하고, 구현 검증과 사람 플레이테스트를 분리한다.
6. 기능 브랜치 + PR, TS strict, npm 단일 lockfile, 빌드 산출물·생성 바이너리 커밋 금지.

## 2. 단계 로드맵

```text
단계 0  전투 증명 (오프라인, 1인)
   │  게이트 G-P0
단계 1  네트워크 수직 절편 (권위 서버, 1~4인, 작은 마을·던전)
   │  게이트 G-P1
단계 2  콘텐츠 절편 완성 (디자인 슬라이스 범위 전체, 클로즈 테스트)
   │  게이트 G-P2
단계 3  출시 준비 (Steam 연동·결제·운영·부하·복구·모더레이션)
   │  게이트 G-P3
단계 4  출시 후 (확장 콘텐츠, 외형 상품 — 사업 승인 시)
```

| 단계 | 답할 질문 | 포함 | 제외 |
|---|---|---|---|
| **0 전투 증명** | 쿼터뷰 + 키보드 분기 콤보 + 히트스톱이 "보상 없이도 다시 싸우고 싶은" 손맛을 내는가(디자인 [G0](../design/concept.md#gates)) | 공유 sim 패키지(30Hz 틱 + §9.5 변환), three.js 클라이언트(S1 결과에 따라 Babylon.js), 환도 1종 콤보 트리 전체, 일반 적 3종(억새 잔향·방패 역졸·그림자 등짐장수), 미니 보스 1(되돌이 삿갓 축소판) — [concept §8.0](../design/concept.md#vertical-slice) 정렬, 히트스톱·카메라·타격음, 회색 상자 또는 임시 모델, 단순 입력 vs 분기 콤보 비교 빌드 | 서버, 계정, 아이템, 퀘스트 |
| **1 네트워크 절편** | 서버 권위 + 예측 하에서 손맛이 유지되고, 마을→파티→던전→보상→포탈→제작 한 바퀴가 데이터 손실 없이 도는가 | Colyseus TownRoom·DungeonRoom(절편 필드 포함)·1인 인스턴스, 예측·재조정, 액션 로컬 시간, 방어자 유리 판정, 전환 프로토콜·귀로등 돌아오는 문, 재접속(5초·잔상·180초·보호 3초), 보스 기여·배율 고정, 원장(드랍·제작·퀘스트 보상), 개발용 Steam 인증 또는 개발 계정, 기본 채팅, 헤드리스 봇, 텔레메트리 기초 | 결제, 대규모 콘텐츠, 운영 도구, 공용 필드(FieldRoom) |
| **2 콘텐츠 절편** | 디자인 슬라이스(퀘스트 12개, 일반 적 6종, 중간보스·보스, 잔향구 2종 — [concept §8.1](../design/concept.md#81-첫-온라인-절편--포함-목록-제안))가 신규 플레이어에게 60~90분 경험을 주는가 | 디자인 slice 범위, 아트 파이프라인 적용 자산, 접근성 필수 항목, 신고·차단, 클로즈 테스트 빌드 배포 | 결제, 확장 지역 |
| **3 출시 준비** | 돈·계정·데이터를 맡길 수 있는가 | Steam 소유권·DLC·마이크로트랜잭션(승인 시) 서버 검증과 대사, Electron 보안 점검, 부하 L3~L6, 복구 훈련, 운영 런북, 모더레이션 도구, 법무(약관·개인정보·등급·AI 공개), 스토어 준비 | — |
| **4 출시 후** | 확장 콘텐츠·외형이 지속 가능한가 | 사업 승인 범위 내 | 가챠·확률형 유료 상품(디자인 범위 외) |

## 5. 사업 모델 제안

### 5.1 구조(제안, 미승인)

| 상품 | 형태 | Steam 구현 후보 | 게임 설계 제약 |
|---|---|---|---|
| **본편** | 유료 패키지 | 기본 앱 소유권 — 서버 `CheckAppOwnership` `[공식: partner.steamgames.com/doc/webapi/ISteamUser]` | — |
| **외형** | 의상·무기 외형·감정표현 | (a) 마이크로트랜잭션 `[공식: /doc/features/microtransactions]` (b) DLC 묶음 (c) Steam Inventory(거래 가능 아이템이 필요할 때) `[공식: /doc/features/inventory]` | 전투 판독성 침해 금지(텔레그래프 색 사용 금지, 실루엣 크기 상한), 능력치 없음 |
| **확장팩** | 새 지역·보스·무기·이야기 | DLC(별도 AppID) — 서버 소유권 검증 `[공식: /doc/store/application/dlc]` | 미보유자와 파티 시 규칙(입장 불가 / 초대받으면 입장) 결정 필요 |

- Steam DLC 문서는 외형·소모품·화폐는 마이크로트랜잭션이 더 적합할 수 있다고 안내한다 `[공식: /doc/store/application/dlc]`. 외형 판매 방식은 단계 3 전에 결정.
- **하지 않는 것(디자인 범위 기준):** 전설 무기·잔향구 판매, 확률형 유료 상품, 능력치 판매. 디자인 P2(전설은 동작을 바꾼다)를 돈으로 우회하지 않는다.
- 서버 운영비가 지속 발생하는 온라인 게임에서 패키지 판매만으로 운영비를 감당할 수 있는지가 핵심 사업 질문이다(§6.3).

### 5.2 가격

가격은 정하지 않는다. 결정 시 필요한 입력: 경쟁작 가격대 조사(출처 기록), 사용자당 월 서버 비용(§6), 목표 판매량 시나리오, 플랫폼 수수료(계약 확인), 환불 정책 영향.

### 5.3 법·플랫폼 확인 목록(모두 `[미검증]`)

- 국내 유통 시 게임물 등급 분류 요건, 해외 등급.
- 유료 아이템 관련 국내 규제(확률형 상품은 없을 예정이나 외형 판매 표시 의무 등).
- Steam 수익 배분·환불 정책·지역 가격.
- 개인정보(채팅 로그·텔레메트리) 국외 이전·보존 기간.
- 생성 AI 도구 출력물의 상업 이용 조건, Steam AI 콘텐츠 공개.

## 6. 비용 구조

### 6.1 항목

| 범주 | 항목 | 시점 | 추정 방법 |
|---|---|---|---|
| 인건비 | §7 역할 × 기간 × 단가 | 전 단계 | 인력 확정 후 |

| 외주 | 전투 애니메이션, 사운드, 음악, 문화 감수, 현지화 | 단계 2~3 | 견적 |
| 도구·라이선스 | 글꼴, 음원, 소프트웨어 | 단계 0~ | 개별 |
| 플랫폼 | Steam 앱 등록비, 수수료 | 단계 3 | 공식 확인 `[미검증]` |
| 법무 | 약관·개인정보·등급·상표 | 단계 3 | 견적 |
| 테스트 | 플레이테스트 사례, 테스트 PC(최소·권장 사양) | 단계 0~ | 개별 |

### 6.2 손익 공식(사업 판단용)

```text
누적 비용(t)      = Σ 인건비 + Σ 외주·도구 + Σ_월 C_mon(t)
본편 순수익       = 판매량 × 순가격(지역 평균, 플랫폼 수수료·환불·세금 차감)
외형·확장 순수익  = Σ 상품 판매량 × 순가격
운영 지속 조건    = 월 순수익(외형·확장 + 신규 본편) ≥ 월 서버 비용 + 월 운영 인건비
사용자당 서버 비용 = C_mon / MAU     (architecture §19)
```

### 6.3 핵심 민감도

- 본편 판매 후 **매출은 감소하지만 서버 비용은 활성 사용자 수만큼 지속**된다. 확장·외형 매출이 이를 메우지 못하면 서버 축소(채널 통합)·리전 축소가 필요.
- 서버 비용을 낮추는 설계 선택: 마을 틱 레이트 낮춤, AOI, 1인 콘텐츠는 서버 룸 대신 오프라인 sim 실행 가능성(치트 시 원장 보상 제한 필요) `[제안 — 보안 검토 필요]`.
