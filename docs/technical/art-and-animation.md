## 1. 아트 디렉션

### 1.1 키워드(제안)

**"먹 번진 안개 속, 단청 한 점의 경고."**

| 축 | 방향 | 피할 것 |
|---|---|---|
| 형태 | 굵은 실루엣, 쿼터뷰에서 읽히는 큰 덩어리(삿갓·도포 자락·무기 길이) | 쿼터뷰에서 뭉개지는 잔디테일 |
| 명도 | 환경은 저채도·중저명도의 수묵 계조, 캐릭터는 환경보다 한 단계 밝게 | 캐릭터와 배경 명도 겹침 |
| 색 | 기본 팔레트는 먹·회청·한지색. **강조색은 의미가 고정됨**(§4.2) | 장식용 원색 남발 |
| 재질 | 한지·삼베·옻칠·녹슨 쇠의 거친 질감, PBR 기반이되 텍스처는 손그림 느낌 | 사실 사진 텍스처 |
| 안개 | 거리 기반 + 높이 안개. 게임 기믹(잔향)과 연결되는 시각 언어 | 판독을 해치는 전체 화면 안개 |

### 1.2 문화 표현 원칙

- 조선에서 **영감**을 받은 가상 세계. 실존 왕·인물·사건·특정 사찰·무속 의례의 정확한 재현을 피한다.
- 종교·장례 의례 모티프(상여, 곡비 등 디자인 문서의 소재)는 **존중하는 표현**을 원칙으로 하고, 외부 감수(문화·민속 자문)를 콘텐츠 확정 전 게이트로 둔다(디자인 가정 A6).
- 한자·한글 표기는 감수 후 확정. 의미 불명 문자 장식 금지.

### 1.3 캐릭터 계층

| 계층 | 판독 우선순위 | 시각 규칙(제안) |
|---|---|---|
| 내 캐릭터 | 1 | 림라이트 또는 발밑 표식, 항상 가장 밝음 |
| 적(위협) | 2 | 공격 텔레그래프 색 고정(§4.2), 정예·보스는 실루엣 크기로 구분 |
| 파티원 | 3 | 이름표 색, 효과 밀도 감소 |
| 낯선 길손(마을) | 4 | 외형(잔향구)은 보이되 효과 최소화 |
| 환경·소품 | 5 | 저채도, 상호작용 가능 물체만 강조 테두리 |

## 2. 카메라

디자인 제안: 고정 각도 쿼터뷰, 요 약 45°·피치 약 50°, 줌 2단계, 회전은 슬라이스 제외([concept.md §5](../design/concept.md)).

| 항목 | 제안 | 검증 |
|---|---|---|
| 투영 | 원근 투영 + 좁은 FOV로 아이소메트릭 느낌 | 직교 투영과 S-A1에서 비교: 원근은 깊이감·타격 카메라 연출에 유리, 직교는 거리 판독에 유리 |
| 추적 | 캐릭터 위치에 감쇠 추적, 공격 방향으로 약간 선행(lead) | 선행 거리 과하면 멀미 — 슬라이더 제공 |
| 가림 처리 | 캐릭터와 카메라 사이 벽·지붕은 디더 투명 또는 컷어웨이 | 마을 지붕 높은 건물에서 테스트 |
| 흔들림 | 히트 강도별 짧은 감쇠 흔들림, 예산 상한(동시 합산 상한) | 접근성 슬라이더(§6) |
| 줌 펀치 | 강공·패링 성공에만 미세 줌 | 남용 시 판독 저하 |
| 보스 프레이밍 | 보스 범위 진입 시 줌아웃 단계 강제 가능 | 보스 크기에 따라 |
| 소프트 록온 | 키보드 전용 모드에서 진행 방향 원뿔 내 최근접 적 | 디자인 입력 체계와 일치 필요 |

카메라 연출은 **표현 시간**(architecture §9)에서만 동작하며 서버 판정에 영향을 주지 않는다.

## 3. UI/UX

### 3.1 원칙

1. 전투 중 화면 중앙은 비운다. 필수 정보는 하단·캐릭터 주변.
2. 키보드 우선: 모든 메뉴는 마우스 없이 조작 가능.
3. 콤보 학습은 **발견 우선**(디자인 G2) — 콤보표를 처음부터 전부 보이지 않고, 사용한 분기를 기록하는 "무예록"으로 노출 `[제안, 디자인 확인 필요]`.

### 3.2 화면 구성(초안)

| 영역 | 내용 |
|---|---|
| 하단 중앙 | 체력·기력, 잔향구 상태, 회피/패링 쿨다운 |
| 캐릭터 발밑 | 콤보 박자 링(접근성 옵션에서 켜기) |
| 좌하단 | 채팅(전투 중 자동 반투명), 파티 |
| 우상단 | 퀘스트 추적(목표 1~2개) |
| 적 머리 위 | 정예 이상만 체력, 상태이상 아이콘 |
| 보스 | 상단 큰 체력바 + 페이즈 표시 |
| 네트워크 | RTT·손실 아이콘(architecture §10) |

### 3.3 마을 사회 UI

- 파티 모집 등불(디자인 용어), 플레이어 상호작용 메뉴: 살펴보기(장비 외형), 파티 초대, 귓속말, 차단, 신고.
- **신고·차단은 2회 클릭 이내** 도달.
- 이름표 표시 거리·인원 상한 옵션(40명 마을 혼잡 대응).

### 3.4 인벤토리·제작

- 원장 확정 전에는 결과를 "처리 중"으로 표시(architecture §13.1). 낙관적 표시 금지.
- 전설 무기 상세: 수치보다 **바뀌는 동작**을 짧은 루프 미리보기 애니메이션으로 보여 준다.
- 제작 확인: 소비 재료 목록 + 결과 + 되돌릴 수 없음 표시.

### 3.5 글꼴·현지화

- 한국어 우선, 영어 후속(디자인 범위). 문자열은 키 기반 외부화.
- 글꼴은 상업용 임베드 가능한 라이선스(예: SIL OFL 계열)만 사용, 파일별 라이선스 기록 `[미검증 — 후보 글꼴 라이선스 개별 확인]`.

## 4. VFX와 판독성

### 4.1 밀도 예산(마을·필드 다수 인원 대응)

| 출처 | 내 화면에서의 VFX 등급 |
|---|---|
| 내 캐릭터 | 전체 |
| 파티원 | 축소(파티클 수·밝기 감소) |
| 낯선 길손 | 최소(히트 스파크만) 또는 끔 — 옵션 |
| 적 텔레그래프 | **항상 전체, 줄이지 않음** |

### 4.2 고정 색 의미(제안)

| 의미 | 색 + 모양(색각 이상 대응으로 모양 병행) |
|---|---|
| 적 공격 범위(회피 가능) | 붉은 계열 + 테두리에서 안으로 차오르는 채움 |
| 패링 가능 공격 | 금색 섬광 + 짧은 링 |
| 패링 불가 공격 | 보라/검은 연기 + 톱니 테두리 |
| 아군 버프·회복 | 청록 + 위로 상승 입자 |
| 잔향(전설) 동작 | 고유 색 1개 무기별 할당 |

### 4.3 기술 메모

- three.js 기준: 인스턴싱된 빌보드 파티클·플립북 텍스처, 트레일은 리본 메시. 구현 방식은 S1 결과에 따라 결정.
- 히트 스파크·타격 플래시는 표현 시간 기준, 히트스톱 동안 정지할 VFX와 진행할 VFX를 데이터로 지정.
- 광과민 대응: 전체 화면 플래시 금지, 플래시 빈도 제한(§6).

| 믹스 옵션 | 마스터·음악·효과·음성·UI·타인 효과음 분리 볼륨 |

## 6. 접근성

| 범주 | 기능(슬라이스 필수 = ●, 출시 = ○) |
|---|---|
| 입력 | ● 키 재매핑 ● 홀드/토글 선택 ● 키보드 전용 모드 ○ 한 손 프리셋 |
| 콤보 보조 | ● 박자 링 표시 ○ 박자 창 완화 옵션(1인 콘텐츠 한정 제안 — 파티 공정성은 디자인 결정) ○ 자동 연속 입력(단순화 모드) |
| 시각 | ● 화면 흔들림·줌 펀치 강도 슬라이더(0 포함) ● 플래시 강도 ● 텔레그래프는 색+모양 이중 부호화 ○ 색각 이상 프리셋 ● UI·자막 크기 |
| 광과민 | 플래시가 초당 3회를 넘지 않도록 설계(WCAG 2.x 2.3.1 "Three Flashes or Below Threshold" 기준 참고 `[미검증 — 원문 재확인]`) |
| 청각 | ● 자막 ● 중요 효과음의 시각 표시(텔레그래프 예고음 대체 아이콘) |
| 인지 | ● 퀘스트 목표 상시 확인 ○ 튜토리얼 재열람 |
| 채팅 | ● 채팅 끄기 ● 낯선 이 채팅 숨김 |

디자인 G8(보조 옵션 켠 비숙련 테스터 완주율) 측정과 연결한다.

## 7. 이미지→3D→리그→애니메이션 파이프라인

### 7.1 전체 흐름

```text
[A 콘셉트]  원화(자체 제작 또는 권리 확보 이미지)·정면/측면 T·A 포즈 시트
     │  출처 기록 시작 (§11)
[B 생성]   이미지→3D (후보: Higgsfield image_to_3d / Meshy Image to 3D API / 수작업 모델링)
     │  원본 GLB 즉시 내부 저장소로 다운로드 + 체크섬 (URL 만료 대응)
[C 정리]   Blender: 스케일·방향·원점, 리토폴/감면, UV, 텍스처 정리, 머티리얼 OPAQUE
[D 리깅]   (a) 생성 도구 자동 리깅(휴머노이드만) 또는 (b) 프로젝트 표준 스켈레톤으로 리그 전이
[E 스킨]   웨이트 점검·수정(망토·소매·치마 등 얇은 부위 수작업)
[F 애니]   (a) 이동·대기·NPC 생활 동작: 라이브러리/생성 클립을 표준 스켈레톤에 리타깃
           (b) 전투 동작: 수작업 키프레임 또는 생성 클립 대폭 수정 + 프레임 마커
[G 내보내기] GLB(계약 §8) + 마커 사이드카 JSON
[H 검증]   glTF-Validator → 계약 검사기 → 최적화(glTF-Transform) → 재검증
[I 검수]   인게임 검수 하니스: 전환·관통·발 미끄러짐·무기 부착 (validation-plan '아트 파이프라인')
```

### 7.2 도구별 확인된 사실

**Higgsfield `game-3d-animation.md`** `[공식: github.com/higgsfield-ai/skills/.../game-3d-animation.md]`
- 목적: 리깅된 다중 클립 GLB 캐릭터 제작.
- 경로: (1) 네이티브 CLI — `image_to_3d` 한 번으로 텍스처·리깅·애니메이션(`--enable_rigging`, `--enable_animation`, `--pose_mode a-pose`, `--animation_action_id`), 추가 클립은 `3d_rigging`; (2) 완전 로컬 — `z_image` T 포즈 참조 → `sam_3_3d` 정적 GLB → 도너 FBX(KayKit·Mixamo 리그)로 `rig_transfer.py`; (3) Meshy API 직접 호출(대체 경로); (4) 비휴머노이드는 절차적 분기; (5) 리깅 없는 소품은 three.js 코드 애니메이션.
- 단계명: Blender 4.2.3 헤드리스 → FBX→GLB 전체 클립 → GLB 검증 → 2D 이미지→애니메이션 GLB(리그 전이) → **Meshy 클립 병합 + 루트 스케일 점검(필수)**.
- 경고: Meshy 라이브러리 `idle`이 루트 스케일 1.176을 굽는 사례 → 스케일 0화·루트 이동 보정 필요. FBX 머티리얼이 `alphaMode: BLEND`로 나와 three.js에서 잘못 렌더 → OPAQUE + doubleSided 권장. 이미지→3D 메시에서 자동 웨이트(`ARMATURE_AUTO`) 실패 → 데이터 전송 방식 웨이트 사용. 얇은 부위 웨이트는 근사치.
- 문서 자체 주장: "2026-06-10 엔드투엔드 검증", 네이티브 경로는 외부 API 키 불필요 — **우리가 검증하지 않음**. Higgsfield·Meshy 출력물 라이선스 문구는 이 문서에 없음.

**Meshy API** `[공식: docs.meshy.ai/en/api/rigging, /animation, /image-to-3d]`
- 인증: `Authorization: Bearer <API_KEY>`.
- Image to 3D: `POST /openapi/v1/image-to-3d`, 입력 이미지 JPG/PNG/WebP ≤20MB, `pose_mode`(a-pose/t-pose), `target_formats`(glb, fbx 등), `enable_pbr`.
- Rigging: `POST /openapi/v1/rigging`, `input_task_id` 또는 `.glb` `model_url`, `height_meters` 기본 1.7. **표준 휴머노이드(이족)만 잘 동작**, 텍스처 없는 메시 미지원, 삼각형 ≤380,000, 얼굴이 +Z를 향해야 함. 출력: 리깅 FBX/GLB + 기본 걷기·달리기.
- Animation: `POST /openapi/v1/animations`, `rig_task_id` + `action_id` 또는 `action_ids`(1~10개를 한 파일로 병합), `post_process.change_fps`(24/25/30/60). 라이브러리 조회 `GET /openapi/v1/animations/library`(크레딧 없음), 카테고리에 Fighting 포함.
- 작업 상태: PENDING → IN_PROGRESS → SUCCEEDED/FAILED/CANCELED. **`expires_at` 이후 파일 삭제 가능** → 즉시 다운로드 필수.
- 문서에 **명시되지 않음**: 뼈 이름·스켈레톤 표준, 요청 속도 제한(별도 페이지 미확인), 크레딧 단가(예시 값만), 생성물 소유권·라이선스 → 모두 `[미검증]`.

### 7.3 판단(제안)

1. **이동·대기·NPC·일반 적**: 생성·라이브러리 클립 + 리타깃으로 속도 확보.
2. **플레이어 전투 동작·보스 핵심 공격**: 수작업 또는 대폭 수정. 이유: 콤보 박자·히트 프레임·캔슬 창을 **프레임 단위로 디자인 데이터와 맞춰야** 하고, 라이브러리 클립은 그 구조를 모른다.
3. **비휴머노이드 보스**(디자인의 `곡비 어멈` 등 형태 미정): 자동 리깅 대상 아님. 수작업 리깅 예산 별도.
4. 생성 도구 출력은 **초안 메시**로 취급. 계약(§8)을 통과하기 전엔 게임에 넣지 않는다.

### 7.4 표준 스켈레톤

- 프로젝트 소유 휴머노이드 스켈레톤 1종(`ym_humanoid_v1`) 정의. 뼈 목록·이름·계층·휴지 포즈(A 또는 T)를 문서화.
- 생성 도구별 뼈 이름 매핑 테이블(Meshy, Mixamo, KayKit 등)을 S-A2에서 실제 출력으로 작성 — Meshy 뼈 이름은 문서에 없음.
- 무기 부착 뼈: `hand_r_weapon`, `hand_l_weapon`, 등·허리 수납 소켓. 무기 GLB는 별도 파일, 부착 오프셋은 무기 데이터.
- 얼굴 표정은 슬라이스 범위 밖(쿼터뷰 거리). 필요 시 블렌드셰이프 별도 계약.

### 7.5 리타깃

- 오프라인(Blender)에서 표준 스켈레톤으로 굽는 것을 기본으로 한다. 런타임 리타깃(three.js `SkeletonUtils` 등)은 의존하지 않는다 — 공식 API 세부 미확인 `[미검증]`, 런타임 비용 회피.
- 리타깃 후 점검: 발 접지(IK 보정 필요 여부), 손 위치(무기 쥠), 루트 스케일 1.0, 루트 이동.

### 7.6 루트 모션과 서버

- 서버는 GLB를 읽지 않는다(architecture §7.5). 동작의 이동량은 **빌드 시 클립 루트 이동을 데이터 곡선으로 추출**해 `content/combat/*.json`에 넣고 서버·클라이언트 sim이 같은 곡선을 쓴다.
- 클라이언트 렌더링에서는 루트 이동을 제거한 인플레이스 클립 + sim 위치를 사용해 서버 보정과 충돌하지 않게 한다 `[제안]`.

## 8. GLB 계약

계약 버전: `ym-glb-contract@1`(초안). 검사기는 `tools/asset-pipeline`에 구현 예정(현재 미구현).

### 8.1 공통

| 항목 | 규칙 |
|---|---|
| 형식 | glTF 2.0 바이너리(`.glb`) |
| 단위·축 | 미터, +Y 위, 캐릭터 정면 +Z(glTF 2.0 규약) |
| 원점 | 캐릭터: 발 사이 바닥. 소품: 바닥 중심 |
| 스케일 | 루트·아마추어 스케일 1.0, 비균일 스케일 금지 |
| 이름 | 소문자 `snake_case`, 접두사로 종류 표시(`chr_`, `wpn_`, `prp_`, `env_`) |
| 머티리얼 | 기본 `alphaMode: OPAQUE`. MASK는 허용 목록(머리카락·나뭇잎), BLEND는 VFX 전용 |
| 텍스처 | 2의 거듭제곱, 최대 해상도는 §10 등급, 최종 배포는 KTX2 또는 WebP(S-A3에서 결정) |
| 압축 | 메시 압축(meshopt/Draco)은 최종 단계에서만, 원본 소스 GLB는 무압축 보관 |
| `extras` | `extras.ym = { contract, assetId, provenanceId, sourceTool }` — **키·URL·개인정보 금지** |
| 검증 | Khronos glTF-Validator 오류 0 `[공식: github.com/KhronosGroup/glTF-Validator]`, 경고는 허용 목록 외 0 |

### 8.2 캐릭터

| 항목 | 규칙 |
|---|---|
| 스켈레톤 | `ym_humanoid_v1` 또는 승인된 몬스터 스켈레톤, 스킨 1개 |
| 정점당 영향 뼈 | 최대 4(`JOINTS_0`/`WEIGHTS_0` 한 세트), 가중치 합 1 |
| 메시 | 의상 파츠별 분리 허용(외형 교체용), 파츠 수 상한은 §10 |
| 애니메이션 | 이 파일에 클립을 넣는 방식과 클립 전용 GLB를 분리하는 방식 중 S-A2에서 결정. 클립 이름은 §8.3 |
| 휴지 포즈 | 바인드 포즈는 표준 스켈레톤 휴지 포즈와 일치 |

### 8.3 클립 이름

`{카테고리}_{무기|공통}_{이름}` 예:

| 카테고리 | 예 |

### 8.4 마커 사이드카(`*.anim.json`)

glTF에는 애니메이션 이벤트 표준이 없으므로 사이드카로 분리한다 `[제안]`.

```json
{
  "contract": "ym-anim-markers@1",
  "clip": "atk_hwando_l2",
  "fps": 30,
  "frames": 24,
  "markers": [
    { "frame": 0,  "type": "startup_begin" },
    { "frame": 7,  "type": "active_begin", "hitbox": "hwando_arc_short" },
    { "frame": 9,  "type": "hit", "hitIndex": 0, "hitstopTicks": 3 },
    { "frame": 10, "type": "active_end" },
    { "frame": 12, "type": "cancel_window_begin", "into": ["atk_hwando_l3", "atk_hwando_h_delay", "def_common_dodge"] },
    { "frame": 18, "type": "cancel_window_end" },
    { "frame": 9,  "type": "sfx", "id": "sfx_hwando_impact_flesh" },
    { "frame": 9,  "type": "vfx", "id": "vfx_hit_spark_steel", "socket": "hand_r_weapon" }
  ],
  "rootMotion": { "extracted": true, "curve": "atk_hwando_l2.root.json" }
}
```

- **전투 판정 정보(active, hit, cancel, hitstop)는 디자인 콤보 데이터가 진실 원천**이며 사이드카는 그 값을 애니메이션 프레임에 정렬하는 도구다. 둘이 다르면 빌드 실패.
- fps는 sim 틱(던전 30Hz 가설)과 맞추거나 정수 배로 둔다 — Meshy `change_fps` 30 옵션 존재 `[공식: docs.meshy.ai/en/api/animation]`.

## 9. Blender QA

### 9.1 자동 검사(헤드리스 Blender + 검사기, 구현 예정)

| 검사 | 실패 조건 |
|---|---|
| 스케일·방향 | 루트/아마추어 스케일 ≠ 1, 정면 ≠ +Z, 원점 위치 벗어남 |
| 루트 스케일 애니메이션 | 어떤 클립이든 루트 스케일 키가 1이 아님(Higgsfield 문서 경고 사례) |
| 스킨 | 정점당 영향 > 4, 가중치 합 ≠ 1, 웨이트 0 정점 |
| 메시 | 예산(§10) 초과, 비다양체, 뒤집힌 노멀 |
| 머티리얼 | 허용 목록 외 BLEND/MASK |
| 텍스처 | 해상도 초과, 누락 |
| 클립 | 이름 규칙 위반, 사이드카 누락, 마커 프레임 > 클립 길이 |
| 메타데이터 | `extras.ym.provenanceId` 누락, `extras`에 금지 키 |

### 9.2 수동 검수(인게임 하니스)

| 항목 | 기준 |
|---|---|
| 전환 | 공격→회피→피격→사망 블렌드에서 튐 없음 |
| 관통 | 무기·망토·소매가 몸 관통 최소(허용 목록화) |
| 발 미끄러짐 | 이동 속도와 클립 보폭 일치 |
| 무기 부착 | 쥔 손 위치·각도, 수납 소켓 |
| 실루엣 | 쿼터뷰 줌 2단계에서 공격 방향이 읽힘 |
| 히트 프레임 | 시각적 접촉 프레임 = 사이드카 `hit` 프레임 ±1 |

### 9.3 Blender 버전

- Higgsfield 문서는 Blender 4.2.3 헤드리스를 사용 `[공식: game-3d-animation.md]`. 우리 파이프라인 버전은 스파이크 시 하나로 고정하고 기록한다. Blender glTF 내보내기 옵션(NLA·샘플링 등) 공식 매뉴얼 페이지는 이번 조회에서 404 → 해당 버전 매뉴얼로 재확인 `[미검증]`.

## 11. 라이선스·출처 기록

### 11.1 자산별 출처 레코드(`provenance/*.json`, 저장소에 커밋 — 생성물 바이너리는 커밋 금지)

```json
{
  "provenanceId": "prv_chr_wanderer_01",
  "assetId": "chr_wanderer_01",
  "inputs": [
    { "kind": "concept_image", "sha256": "…", "author": "내부 아티스트 A", "rights": "work_for_hire" }
  ],
  "steps": [
    { "tool": "meshy", "endpoint": "image-to-3d", "model": "meshy-6", "taskId": "…", "date": "YYYY-MM-DD", "tosSnapshot": "docs/legal/tos/meshy-YYYYMMDD.pdf" },
    { "tool": "blender", "version": "x.y.z", "operator": "B", "notes": "retopo, uv" }
  ],
  "thirdParty": [
    { "name": "KayKit …", "license": "CC0 (원문 파일 확인 필요)", "url": "…", "licenseFileSha256": "…" }
  ],
  "aiGenerated": true,
  "outputSha256": "…",
  "reviewedBy": null
}
```

### 11.2 규칙

1. **입력 이미지 권리**: 내부 제작 또는 명시적 권리 확보 이미지만. 타 게임·작품·실존 인물 이미지 입력 금지.
2. **생성 도구 약관**: Higgsfield·Meshy 출력물 상업 이용·소유권 조건은 이번 조사에서 확인하지 못했다 `[미검증]`. 사용 시점의 약관과 요금제 조건을 스냅샷 보관하고 **법무 검토 통과 전 출시 빌드 포함 금지**.
3. **CC0 팩**(KayKit·Quaternius·Kenney): Higgsfield 문서가 CC0로 소개하지만 **각 팩의 라이선스 파일을 직접 확인**하고 해시 기록 `[미검증]`.
4. **Mixamo**: Higgsfield 문서가 도너 리그·수동 단계로 언급. 이용 조건 `[미검증]` — 확인 전 사용 보류.
5. **Steam AI 생성 콘텐츠 공개**: Steam 스토어 제출 시 AI 생성 콘텐츠 공개 절차가 있는 것으로 알려져 있음 `[미검증 — Steamworks 문서 확인 필요]`. 출처 레코드의 `aiGenerated` 필드로 집계 가능하게 유지.
6. 음악·효과음·글꼴도 같은 레코드 형식으로 관리.

| 사용자별 키 | 공유 키 대신 작업자별 키(가능한 경우)로 사용량·책임 추적 |
| 회전 | 퇴사·유출 의심 시 즉시, 정기 회전 주기 운영 문서화 |
| 로그 | 요청 로그에서 `Authorization` 헤더 마스킹 |
| 결과 URL | 생성 결과 URL은 만료형(`expires_at`) `[공식: docs.meshy.ai]` → 즉시 내부 저장소로 복사 후 체크섬, URL은 레코드에 남기지 않음(작업 ID만) |
| 데이터 업로드 | 콘셉트 이미지를 외부 서비스에 올리는 것 자체가 외부 전송 — 미공개 원화 업로드는 승인 후 |
| 승인 | 유료 생성 작업은 현재 미승인. 착수 전 코디네이터/사용자 승인 필요 |

## 13. 생성 비용 예산

단가는 확인하지 않았다(Meshy 문서에는 예시 크레딧 값만 존재) `[미검증]`. 공식만 정의한다.

```text
캐릭터 1종 생성 비용 ≈ 시도 횟수(k) × (이미지→3D 크레딧 + 리깅 크레딧 + Σ 애니메이션 액션 크레딧)
  - Meshy animation: action_ids의 액션마다 과금 [공식: docs.meshy.ai/en/api/animation]
  - PENDING 작업 삭제는 환불, 완료 작업은 환불 없음 [공식: docs.meshy.ai/en/api/rigging]
총 생성 비용 = Σ_자산종류 (자산 수 × 캐릭터당 비용) + 실패·재시도 버퍼
수작업 비용  = Σ (정리·리깅·웨이트·전투 애니메이션 시간) × 인건비 단가
```

- 의사결정 지표: **"게임에 들어간 자산 1개당 총비용(생성 + 수작업 정리)"**. 생성 자체가 싸도 정리 시간이 크면 수작업이 나을 수 있다 — S-A2에서 실측.

## 14. 아트 스파이크

| ID | 질문 | 방법 | 산출물 |
|---|---|---|---|
| S-A1 카메라 | 원근 vs 직교, 피치·FOV | 회색 상자 전투장 + 플레이테스트 | 카메라 파라미터 표 |
| S-A2 리그 파이프라인 | 생성 캐릭터 1체를 표준 스켈레톤으로 전이하고 환도 공격 3개 + 회피·피격·사망을 붙일 수 있나 | Higgsfield 또는 Meshy 1회(승인 후) + 수작업 대조군 | 뼈 매핑 표, 결함 목록, 자산당 소요 시간 |
| S-A3 압축·로딩 | KTX2 vs WebP, meshopt vs Draco | glTF-Transform `optimize`/`meshopt`/`draco`/`resize` 비교 `[공식: gltf-transform.dev]` | 크기·로딩 시간·화질 표 |
| S-A4 판독성 | 마을 40명 + 텔레그래프가 읽히나 | S1 벤치 씬 + 테스터 | VFX 밀도 등급 확정 |
| S-A5 히트스톱 연출 | 히트스톱 길이·카메라·사운드 조합 | 1인 오프라인 전투 실험 | 히트스톱 데이터 테이블 초안 |
