## 0. 한 장 요약 (구현 카드)

코디네이터 축소 지침 반영: **9열 × 12행, 타일 ≈ 40 px, 맵 팬 없음, 건물 6종, 자동화 2종, 액티브 2종, 8웨이브.**

| 항목 | 확정값 |
|---|---|
| 화면 | 세로 393×852 기준 / 최소 360×640. 상태 리본 56 px · 월드 62~66% · 컨텍스트 트레이 132 px(선택 시) · 커맨드 도크 104 px |
| 전장 | 9×12가 **스크롤 없이 한 화면**. 타일 하한 40 px, 미달 시 월드 비율을 올려 흡수 |
| 탭 안전장치 | 선택은 스냅(반경 24 px), **확정은 항상 화면 좌표 56 px 버튼** |
| 건설 | 타일 탭 → 반원 건설 링(슬롯 56 px) → 고스트 실시간 미리보기 → **명시적 확정 버튼** → 3초 취소 토스트 |
| 색 | `ink.*` 4단 물 + 고채도는 광원·위협·UI만. 동시 3계열 상한. 색+형태+움직임 3중 부호화 |
| 형태 | 캡슐/육각 + 3단 셰이딩 + 림라이트. 티어는 색이 아니라 **실루엣**으로 오른다 |
| 레이어 | L0~L10, 정적 레이어는 오프스크린 캐시 (L4.5 전력망 포함) |
| 예산 | 시뮬 3 ms + 렌더 8 ms ≤ 16.6 ms. 22 ms 초과 시 품질 강등. 파티클 180/90/0 |
| 경고 | T−20/12/6/3/0 5단계. **무음에서 100% 전달**, 항상 방향 포함 |
| 해금 | 4.2 s 7비트, 스킵 가능, 반복은 0.9 s 축약, 연출 중 게임 시간 정지 |
| 잠수정 | 모드 아님. 상시 유닛 + 좌측 홀드 조이스틱 + 액티브 2버튼, 조준 자동 |
| 금지 | 이모지, `ctx.filter`, 대시보드 카드, 메뉴 깊이 3+, 맵 필수 패닝, 확정 없는 즉시 소모 |

**먼저 정해야 할 것**: §18.5의 D0(Phaser 제거 여부) · D2(완전 봉쇄 허용 여부). 나머지는 병행 가능합니다.

## 1. 한 문장 목표

> **"수심 아래에서 내 기지가 자라는 걸 눈으로 본다."**

플레이어가 화면을 켜고 3초 안에 (1) 내 기지가 어디까지 커졌는지, (2) 어느 통로가 위험한지, (3) 지금 누를 수 있는 가장 좋은 수가 무엇인지를 **글자를 읽지 않고** 알아야 합니다. 숫자는 확인용이지 판단의 1차 채널이 아닙니다.

## 2. 무엇을 버리는가 (Anti-goals)

기존 프로토타입(`index.html`의 아비스 다이버 v2, `src/mobile-renderer.ts`)에서 반복적으로 나타난 문제를 명시적으로 금지합니다.

| 버리는 것 | 왜 문제였나 | 대체 |
|---|---|---|
| 1990년대식 원시 도형 나열 | 단색 `fillRect`/`ellipse`를 평면으로 쌓아 재질·깊이가 없음 (`renderer.ts` 전반) | §5 3단 셰이딩 램프 + 림라이트 + 캐스틱 |
| 이모지·기호 플레이스홀더 | 스타일이 OS마다 달라지고 게임 세계와 분리됨 | 코드로 그린 **아이콘 픽토그램 세트**(§5.6) |
| 작은 격자 셀 | 손가락보다 작은 타깃, 시각적으로 스프레드시트 | 타일 하한 **40 px** + 선택은 24 px 스냅, **확정 버튼은 항상 56 px** (§7.4, §18.2-X1) |
| 일반적인 대시보드 카드 | "게임"이 아니라 관리 도구로 보임 | 월드 위에 얹는 **디제틱 HUD**(선체 계기 톤, §7) |
| 메뉴 다층 구조 | 모바일에서 깊이 2 이상이면 이탈 | 최대 깊이 **2**, 주요 행동은 전부 **1탭**(§8) |
| 얕은 리스킨 | 같은 루프에 색만 바꾸기 | 전략 3종이 **실루엣부터 다르게** 자람(§9) |
| 무한 반복 클릭 | 손가락 노동 | 해결된 작업은 자동화로 승격, 연출로 보상(§10) |

## 3. 아트 필러 4

1. **압력과 빛** — 심해의 주인공은 어둠이 아니라 *어둠 속의 한정된 빛*이다. 모든 형태는 광원(기지 창, 탐조등, 생체발광, 용암)으로부터 읽힌다.
2. **실루엣 우선** — 어떤 구조물도 검은 실루엣만으로 종류가 구분되어야 한다. 색·디테일은 두 번째 채널.
3. **살아 있는 물** — 정지 화면이 없다. 부유물, 조류, 열수, 광선이 항상 아주 느리게 흐른다(감속 모드에서는 정지).
4. **성장의 가시성** — 업그레이드는 숫자가 아니라 **형태 변화**로 먼저 보인다. 티어가 오르면 실루엣이 바뀐다.

**규칙**
- 물 배경은 **깊이에 따라 4단 그라디언트**로만 만들고, 채도 높은 색은 전부 광원·UI·위협에만 쓴다. 심해가 알록달록해지는 순간 싸구려가 된다.
- 한 화면에 동시에 존재하는 **고채도 색은 최대 3계열**. 예: 아군 시안 + 위협 레드 + 자원 골드. 보라(해금)가 등장하면 §11 연출 동안 다른 계열을 40% 디밍한다.
- 위협 색은 물 배경 대비 **명도 대비 3:1 이상**을 유지한다(`threat.red` on `ink.mid` = 4.1:1, 통과).

### 4.2 색맹 안전 규칙 (필수)

색 하나로만 정보를 전달하지 않는다. 모든 상태는 **색 + 형태 + 움직임** 3중 부호화.

| 상태 | 색 | 형태 | 움직임 |
|---|---|---|---|
| 아군/안전 | 시안 | 둥근 모서리, 수평 라인 | 느린 호흡(2.4s 사인) |
| 위협 | 레드 | 각진 스파이크, 비대칭 | 불규칙 저크(0.2~0.5s) |
| 경고/예고 | 앰버 | 삼각 셰브런 | 리듬 펄스(0.8s 등간격) |
| 미지/해금 | 바이올렛 | 육각 프리즘 | 굴절 흔들림 |

### 4.3 깊이 = 대기 원근

카메라 깊이 `d`(0=상층, 1=최심부)에 따라 전 레이어에 동일 규칙을 적용한다.

- 원경 레이어: 채도 ×0.35, 물색으로 `lerp` 0.55, 명도 −25%
- 중경: 채도 ×0.7, `lerp` 0.25
- 근경/기지: 원색 유지 + 림라이트
- 최근경(부유물): 블러 대체로 알파 0.25 + 크기 2배 (실제 블러 필터 금지, §6.3)

## 5. 렌더링 기법 스택 (전부 Canvas 2D로 구현 가능)

외부 이미지 자산 없이 코드로만 그립니다(기존 프로젝트 원칙 유지). 아래는 "프리미티브 나열"에서 벗어나기 위한 **구체적 기법 목록**이며, 각 항목은 후속 렌더러 태스크의 체크 항목이 됩니다.

### 5.1 레이어 스택 (뒤 → 앞)

| # | 레이어 | 내용 | 갱신 |
|---|---|---|---|
| L0 | 심연 그라디언트 | 세로 4스톱 `createLinearGradient` + 비네트 | 깊이 변경 시만 |
| L1 | 원경 실루엣 | 해구 벽·열수구 능선, 단색 실루엣 2겹 패럴랙스 0.15 / 0.3 | 카메라 이동 시 (오프스크린 캐시) |
| L2 | 광선 | 상층 태양광 4~6줄 / 심층 열수 발광, 사다리꼴 그라디언트 + `lighter` | 매 프레임 (저비용) |
| L3 | 지형 | 기지가 붙는 암반, 3단 램프 + 이끼 노이즈 점묘 | 지형 변경 시 (캐시) |
| L4 | 구조물 그림자 | 지형 위 타원 그림자 + 접지 어두움 | 건설 시 (캐시) |
| L5 | 구조물 | 기지 모듈 본체 (§5.4) | 상태 변경 시 캐시, 애니 파트만 매 프레임 |
| L6 | 유닛·위협 | 드론, 해양 생물, 투사체 | 매 프레임 |
| L7 | 이펙트 | 폭발, 스파크, 충격파, 데미지 넘버 | 매 프레임 |
| L8 | 부유물 | 근경 마린 스노우, 알파 0.25 | 매 프레임 |
| L9 | 조명 합성 | `globalCompositeOperation = 'lighter'` 글로우 패스 | 매 프레임 |
| L10 | HUD | §7 | 값 변경 시 |

**L1/L3/L4/L5는 오프스크린 캔버스에 캐시**하고 매 프레임 `drawImage` 한 번으로 합성합니다. 이것이 현재 코드(`renderer.ts`가 매 프레임 수백 개 도형을 새로 그림)와의 가장 큰 구조적 차이입니다.

### 5.2 3단 셰이딩 램프 — "평면 도형"에서 벗어나는 핵심

모든 구조물 면은 **하이라이트 / 기본 / 그림자** 3색을 항상 함께 칠합니다. 광원은 **화면 좌상단 고정 + 기지 내부광**의 2광원.

```
면 그리기 = polygon(기본색)
          + polygon(상단 1/3 오프셋, 하이라이트, alpha .55)
          + polygon(하단 1/4 오프셋, 그림자, alpha .5)
          + stroke(림라이트 1px, 광원 반대편 가장자리, energy.cyan alpha .35)
```

림라이트 한 줄이 심해 물체를 "물속에 있는 것"으로 만듭니다. 이게 없으면 아무리 색을 바꿔도 90년대 도형으로 보입니다.

### 5.3 발광과 블룸 (라이트 버전)

- 진짜 블러(`ctx.filter = 'blur()'`)는 모바일에서 프레임을 잡아먹으므로 **금지**.
- 대신 **다중 알파 스택**: 같은 원을 반지름 ×1.0/×1.8/×3.2, 알파 .5/.22/.08로 `lighter` 합성. 3번의 `arc` fill로 충분히 블룸처럼 보입니다.
- 창문·계기 등 작은 광원은 **radial gradient 1개 + 코어 점 1개**.
- 화면 전체 플래시는 알파 0.35 이하, 지속 120ms 이하. 감속 모드에서는 알파 0.12.

### 5.4 구조물 형태 문법

기지 모듈은 공통 문법을 공유해서 "한 세계의 물건"으로 보이게 합니다.

- **기본 형태**: 가로로 눕힌 캡슐(압력 용기) 또는 육각 프리즘. 직각 사각형 금지.
- **접합부**: 모든 모듈은 지름 12px의 원형 도킹 칼라로 연결. 도관은 두 겹 라인(외피 `hull.lo` 6px + 내부 `energy.cyan` 2px 흐름 애니).
- **디테일 3요소**: ① 창 2~4개(`glass.warm`), ② 리브(늑재) 3~5줄, ③ 기능 파트 1개(레이더/포신/집게/굴뚝). 이 셋이 있으면 실루엣만으로 종류가 구분됩니다.
- **티어 표현**: 티어가 오르면 색이 아니라 **형태**가 바뀐다.
  - T1: 민무늬 캡슐 + 창 2
  - T2: 외부 보강 프레임 추가 + 창 4 + 기능 파트 확대
  - T3: 상부 증축 실루엣 + 발광 트림 라인 + 고유 애니메이션 파트(회전 레이더/맥동 코어)

### 5.5 애니메이션 문법

| 대상 | 움직임 | 주기 |
|---|---|---|
| 기지 전체 | 없음(고정). 흔들리면 조작감이 나빠짐 | — |
| 도관 에너지 | 대시 오프셋 흐름 | 1.6 s/루프 |
| 창 불빛 | 개별 랜덤 위상 미세 깜빡임 알파 ±0.08 | 3~7 s |
| 드론 | 목표까지 이징(easeInOutQuad) + 도착 시 오버슈트 6% | 이동거리 비례 |
| 위협 생물 | 몸통 사인 웨이브(꼬리로 갈수록 진폭 증가) | 0.9~1.4 s |
| 부유물 | 상승 + 좌우 표류 | 12~20 s |

### 5.6 아이콘 픽토그램 (이모지 대체)

자원·행동 아이콘은 **12×12 그리드 위 벡터 패스**로 정의하고 단색 + 1px 하이라이트로 그립니다. 최소 12종: 전력, 산소, 광물, 유기물, 연구, 인력, 건설, 철거, 업그레이드, 자동화, 경고, 잠금.
어떤 상황에서도 시스템 폰트 이모지를 그리지 않습니다.

## 7. 화면 계층 (세로 모바일 우선)

기준 해상도 **393 × 852 CSS px**(현대 안드로이드 중앙값), 최소 지원 **360 × 640**. 가로 모드는 월드 뷰포트만 넓히고 도크를 우측으로 옮기는 동일 레이아웃을 사용합니다.

### 7.1 영역 배치

```
┌───────────────────────────────────────┐  ← safe-area-inset-top
│ A. 상태 리본            56 px          │
├───────────────────────────────────────┤
│                                       │
│                                       │
│ B. 월드 뷰포트                         │
│    (가변, 화면의 58~64%)               │
│                                       │
│   ┌E┐                          ┌F┐    │  E=위협 나침반  F=잠수정 액티브 2
│   └─┘                          └─┘    │
├───────────────────────────────────────┤
│ C. 컨텍스트 트레이  0 또는 132 px       │  ← 선택 시에만 펼침
├───────────────────────────────────────┤
│ D. 커맨드 도크         104 px          │
└───────────────────────────────────────┘  ← safe-area-inset-bottom
```

| 영역 | 내용 | 규칙 |
|---|---|---|
| **A 상태 리본** | 1차 자원 3개(전력·산소·광물) + 수심 + 다음 웨이브 타이머 | 항목 6개 초과 금지. 값 변화는 숫자 롤링 + 아이콘 펄스. 남는 자원은 트레이에서만 본다 |
| **B 월드 뷰포트** | 기지·지형·위협. 핀치 줌 0.6~2.2배, 1핑거 팬 | 게임의 주인공. 어떤 UI도 여기를 40% 넘게 덮지 않는다 |
| **C 컨텍스트 트레이** | 선택한 모듈/타일의 행동 3~5개 | 선택 시 180 ms에 슬라이드업. 비선택 시 높이 0 |
| **D 커맨드 도크** | 상시 5슬롯: 건설 / 자동화 / 연구 / 조타(직접조작) / 로그 | 아이콘 + 한글 라벨 2~4자. 배지로 "지금 가능한 수" 표시 |
| **E 위협 나침반** | 좌측 가장자리, 화면 밖 위협 방향·거리 | 위협 있을 때만 표시 |
| ~~F 카메라 홈~~ | **삭제** — 전장이 한 화면에 들어오므로 불필요 (§18.2-X1). 그 자리는 §8.4 잠수정 액티브 버튼이 차지한다 | — |

### 7.2 시선 우선순위

1순위 = 월드의 **변화**(폭발, 완성, 침입). 2순위 = 도크 배지. 3순위 = 상태 리본 숫자.
따라서 **상태 리본은 절대 애니메이션으로 시선을 뺏지 않습니다**(값 변경 펄스는 120 ms, 알파 0.3 이내).

### 7.3 디제틱 HUD 톤

HUD는 "일반적인 앱 카드"가 아니라 **잠수정 계기판**입니다.
- 패널 배경: `ink.deep` 알파 0.82 + 상단 1px `energy.cyan` 알파 0.25 하이라이트 + 미세 스캔라인(4px 간격, 알파 0.04)
- 모서리: 4px 라운드 + 좌상/우하 모서리만 사선 컷(6px) → 기계적 인상
- 그림자 대신 **아래쪽 2px 시안 라인**으로 부양감 표현
- 카드 나열 금지: 정보는 **행(row)** 으로 쌓고, 구분은 1px 라인으로만

| 항목 | 최소값 |
|---|---|
| 탭 타깃 | 48 × 48 CSS px (인접 타깃 간격 ≥ 8 px) |
| 월드 타일 | 하한 **40 px**. 탭은 반경 24 px 스냅으로 최근접 유효 타일을 잡는다 |

## 8. 맵 · 커맨드 인터랙션

### 8.1 제스처 사전 (전부 이것만, 추가 금지)

| 제스처 | 결과 |
|---|---|
| **탭 (빈 타일)** | 건설 링 열림 (§8.2) |
| **탭 (내 모듈)** | 선택 + 컨텍스트 트레이 펼침 |
| **탭 (위협)** | 조준 표시 + 정보 캘아웃 1.5 s |
| **롱프레스 400 ms** | 상세 카드(수치 전체) — 이 게임에서 숫자를 깊게 보는 유일한 경로 |
| **드래그 (모듈 → 타일)** | 이동/재배치. 유효 타일 하이라이트, 무효 시 붉은 X + 스냅백 |
| ~~드래그 (빈 곳) = 카메라 팬~~ | **삭제** — 스크롤 없는 전장 채택 시 (§18.2-X1) |
| **좌측 빈 물 홀드** | 그 자리에 잠수정 가상 조이스틱 생성 (§8.4) |
| **핀치** | 접근성 확대 전용 1.0~1.6× (플레이에 필수 아님) |
| **두 손가락 탭** | 시간 배속 토글 (1× / 2×) |
| **도크 조타 버튼 홀드** | 직접 조작 모드 (§8.4) |

더블탭은 쓰지 않습니다(팬·줌과 충돌하고 오탐이 많음).

### 8.2 건설 링 — 메뉴 대신 원형 팔레트

빈 타일 탭 → 그 타일을 중심으로 **반경 96 px의 반원/원형 링**에 후보 4~6개가 100 ms 스태거로 피어납니다.

- 각 슬롯은 지름 **56 px** 원형, 픽토그램 + 비용 배지
- 손가락이 화면 아래·가장자리에 있으면 링이 자동으로 **반원으로 접혀** 항상 화면 안에 들어옵니다
- 슬롯 위로 손가락을 끌면 그 자리에 **고스트 프리뷰**가 실제 크기로 즉시 렌더됩니다 — 확인 다이얼로그 없음
- 고스트는 동시에 **영향 오버레이**를 그립니다: 사거리 원(시안 점선), 통로 차단 여부(붉은/시안 통로 하이라이트), 인접 보너스(연결선)
- **확정은 명시적으로 받습니다**(코디네이터 지침). 손을 떼면 고스트가 그 타일에 **확정 대기 상태**로 남고, 타일 옆에 지름 **56 px 확정 버튼(체크)** 과 **48 px 취소(X)** 가 뜹니다. 확정 전까지 비용은 차감되지 않으며, 영향 오버레이는 계속 보입니다.
- 다른 곳을 탭하면 대기 상태가 취소됩니다. **모달 다이얼로그는 쓰지 않습니다** — 확정 버튼은 월드 위에 떠 있는 요소이고 화면을 덮지 않습니다.
- 확정 후에도 **3초 토스트의 "취소"** 로 되돌릴 수 있습니다(전액 환불).

이 방식이 "메뉴 과다"와 "작은 격자"를 동시에 해결합니다.

### 8.3 통로 방어(초크) 인터랙션

지형은 자유 격자가 아니라 **해구 통로 그래프**입니다. 통로에는 폭(1~3)이 있고, 폭이 좁을수록 방어 효율이 높습니다.

- 통로는 평소 은은한 시안 흐름선으로 표시. 위협 접근 시 해당 통로가 **레드로 물들며 흐름 방향이 역전**됩니다 — 어디로 오는지 글자 없이 읽힙니다.
- 방벽 배치 시 **차단 미리보기**: 막으면 위협 경로가 실시간으로 재계산되어 **점선 경로 애니메이션**으로 새 경로를 보여줍니다. "여기 막으면 저리로 돌아간다"가 즉시 보입니다.
- 완전 봉쇄가 불가능한 지점은 통로 입구에 **부서진 육각 아이콘**으로 상시 표시(시행착오 방지).

### 8.4 직접 조작(잠수정) — 모드가 아니라 상시 존재

> 게임디자인 초안 §5와 맞추어 개정했습니다. 잠수정은 "모드"가 아니라 **월드에 항상 있는 유닛**입니다.

- 조작하지 않으면 잠수정은 코어 옆에 **정박한 채 조명만 켜고 대기**합니다. 화면에 계속 보이므로 "쓸 수 있다"는 사실을 배울 필요가 없습니다.
- **화면 좌측 절반의 빈 물 영역을 눌러 유지**하면 그 자리에 가상 스틱이 생성됩니다(고정 위치 스틱 아님). 우측 하단에 **액티브 2버튼**(축소 범위 확정: 용접 / 견인), 지름 **56 px**, 간격 12 px. 쿨다운은 버튼 테두리를 도는 시계 방향 원호로 표시하고 숫자를 얹지 않습니다.
- 조준은 자동(최근접 적). **플레이어에게 조준 노동을 시키지 않습니다.**
- 스틱에서 손을 떼면 2초 뒤 정박 복귀. 별도 종료 버튼 없음.
- 잠수정에는 항상 **따뜻한 탐조등 콘(반경 3타일, `glass.warm` 알파 0.12)** 이 붙습니다. 심해 암흑 구역에서는 이 콘이 곧 시야이고, 그것만으로 "직접 나가면 보이는 게 늘어난다"가 전달됩니다.
- **완전히 선택적**: 방치해도 지지 않습니다(게임디자인 §5 계약). 직접 조작 중에도 상태 리본과 웨이브 경고는 절대 가리지 않습니다.
- **코어 조각 회수(12초 소멸)** 는 직접 조작의 유일한 시간 압박입니다. 그래서 조각에는 전용 판독 규칙을 둡니다: `arcane.violet` 조각 위에 **줄어드는 링**(잔여 시간 = 링 각도), 남은 3초부터 링이 레드로 전환 + 0.5 s 주기 펄스, 화면 밖이면 §7.1 위협 나침반과 **같은 축의 반대편(우측)** 에 보라 화살표. 자원 아이콘 위에 숫자 타이머를 얹지 않습니다.

### 8.5 피드백 규칙

모든 입력은 **150 ms 안에** 시각 반응이 있어야 합니다.
탭 = 접촉점 링 확산(빠름 120 ms) + 짧은 햅틱(10 ms). 유효하지 않은 입력 = 8 px 좌우 셰이크 + 저음 톤. 무반응은 버그로 취급합니다.

## 9. 기지 전략 3종의 가시적 차이

세 전략은 **스탯이 아니라 기지의 생김새**로 갈립니다. 스크린샷 한 장만 봐도 어떤 전략인지 알아야 합니다.

### 9.1 요새 (봉쇄형)

| 채널 | 표현 |
|---|---|
| 배치 | 통로 입구에 밀집, 세로로 두꺼운 벽 실루엣. 기지 폭이 좁고 높다 |
| 형태 | 각진 장갑판, 외부 리브 굵음, 포신·차폐막 |
| 색·광 | `alert.amber` 경계등이 통로 쪽으로 회전 스캔, 내부광 최소 |
| 파티클 | 방벽 표면 스파크, 피격 시 장갑 파편 |
| 지형 변화 | 통로가 물리적으로 좁아지고 잔해가 쌓임 |
| 사운드 | 낮은 금속 진동 앰비언스, 방어 성공 시 묵직한 임팩트 |

### 9.2 산업 (확장형)

| 채널 | 표현 |
|---|---|
| 배치 | 자원 노드로 도관이 방사형으로 뻗음. 기지가 **넓게 퍼진다** |
| 형태 | 컨베이어, 채굴 리그, 굴뚝, 저장 탱크(원통 반복) |
| 색·광 | `ore.gold` 도관 흐름이 눈에 띄게 빠름, 굴뚝 열수 플룸 |
| 파티클 | 도관 안 광물 입자가 실제로 흘러 들어옴(입고 시 저장탱크 게이지 상승) |
| 지형 변화 | 채굴한 노드가 파여 들어가며 지형이 실제로 변한다 |
| 사운드 | 리듬감 있는 기계 루프, 입고 시 짧은 상승 아르페지오 |

### 9.3 연구 (심층형)

| 채널 | 표현 |
|---|---|
| 배치 | 유기적 곡선 배열, 기지가 **아래로 깊게** 자란다 |
| 형태 | 유리 돔, 생체 배양 튜브, 프리즘 안테나 |
| 색·광 | `arcane.violet` 맥동, 돔 안 실루엣이 움직임 |
| 파티클 | 드론 군집이 기지 주위를 궤도 비행, 해금 임박 시 밀도 증가 |
| 지형 변화 | 미지 구조물(고대 유적)이 조명으로 서서히 드러남 |
| 사운드 | 하모닉 패드, 이질적 초음파 핑 |

### 9.4 게임디자인 초안 A/B/C와의 매핑 (개정)

게임디자인 초안 §11이 전략을 **A 협곡 봉쇄형 / B 유인 감속형 / C 전진 채굴형**으로 훨씬 구체적으로 정의했습니다. 위 9.1~9.3의 이름(요새/산업/연구)은 **폐기**하고, **6채널 시각 문법은 그대로 A/B/C에 재배치**합니다.

| 채널 | **A 협곡 봉쇄** | **B 유인 감속** | **C 전진 채굴** |
|---|---|---|---|
| 배치 (실루엣) | 코어 반경 4에 **밀집·수직 벽**. 폭 좁고 두껍다 (9.1 유지) | 넓고 **낮게 퍼진 저층 격자**, 꺾인 벽 두 겹 | 균열 방향으로 **길게 뻗은 촉수형 체인** (9.2 도관 문법 재사용) |
| 형태 | 각진 장갑판, 굵은 리브, 작살포/분쇄기 | 낮은 해벽 + 유기적 해초·포자 실루엣, 부드러운 곡선 | 송전탑(가늘고 높음) + 전진 부표. 세로 요소가 리듬을 만든다 |
| 색·광 | `alert.amber` 경계등, 내부광 최소 | `arcane.violet` 감속장 + `energy.cyan` 코일 아크 (9.3 바이올렛 재사용) | `ore.gold` 송전 체인 흐름 + 균열 쪽 `threat.red` 근접 |
| 파티클 | 장갑 파편, 용접 스파크 | 포자 구름(느린 부유), 점착 해초 늘어짐 | 채굴 입자가 체인을 타고 **뒤로** 흐름 |
| 지형 변화 | 램프가 물리적으로 좁아지고 잔해가 쌓임 | 바닥이 해초로 덮여 색이 바뀜 | 균열 주변이 파여 들어감 |
| 사운드 | 낮은 금속 진동, 묵직한 임팩트 | 거의 무음 + 간헐 아크 스냅 (방치 친화가 소리로도 들림) | 리듬 기계 루프 + 전방 교전음 |
| **한눈 판독** | "벽이 두껍다" | "바닥이 넓게 덮였다" | "선이 위로 뻗었다" |

세 전략은 **면(A) / 바닥(B) / 선(C)** 이라는 서로 다른 기하 요소를 점유하므로, 스크린샷 한 장에서 즉시 구분되고 섞어 지어도 시각적으로 충돌하지 않습니다. 색 계열도 앰버 / 바이올렛+시안 / 골드로 분리되어 §4.1의 "동시 3계열" 상한 안에 들어옵니다.

**혼합 플레이**도 화면에 그대로 보입니다: 요새 벽 뒤로 산업 도관이 흐르고 그 아래 연구 돔이 빛나는 식으로, 세 언어가 겹쳐도 서로 침범하지 않게 **색 계열(앰버/골드/바이올렛)을 분리**했습니다.

## 10. 성장 · 자동화의 가시화

### 10.1 "빠르게 커진다"를 만드는 연출 규칙

- **건설은 즉시 실루엣이 생긴다.** 진행 바가 아니라 **반투명 골조 → 채워짐** 으로 표현. 대기 중에도 기지가 커 보입니다.
- 완성 순간: 도킹 칼라에서 시안 링 1개가 0.35 s 확산 + 내부 창에 순차 점등(모듈당 창 4개, 60 ms 간격).
- **10분 전후로 화면 밀도가 눈에 띄게 달라져야 합니다.** 초반 모듈 3개 → 중반 12개 → 후반 30개+ 규모를 상정하고, 줌 아웃 시 원경 실루엣으로도 "커졌다"가 읽히게 실루엣 상단선을 계속 갱신합니다.

### 10.2 자동화 승격 연출

같은 조작을 일정 횟수 반복하면 그 작업이 자동화 후보가 됩니다. 반복 클릭을 **없애는 것 자체가 보상**이 되도록 연출합니다.

1. 임계 도달 시 도크 **자동화** 버튼에 시안 배지 + 1회 펄스
2. 열면 "이 작업을 드론에게 넘기시겠습니까" 1행 카드 (선택지 2개, 깊이 1)
3. 승인 시: 해당 작업 아이콘이 손가락 아이콘 → 드론 아이콘으로 **모프**(400 ms), 실제 드론이 기지에서 출항해 그 일을 하러 갑니다
4. **개정(게임디자인 §6 반영)**: 자동화는 수동의 **70% 효율**이므로 수동 버튼을 없애면 안 됩니다. 대신 버튼의 **역할이 바뀌는 것**을 보여줍니다 — 배지가 `필요`(앰버, 깜빡임)에서 `선택`(시안, 정적)으로 바뀌고, 아이콘 둘레를 작은 드론 글리프가 천천히 공전합니다. "안 눌러도 돌아가지만, 누르면 더 낫다"가 한눈에 읽혀야 합니다.
5. 자동화 장치는 **전력을 먹습니다.** 승격 순간 전력 게이지에서 해당 소비량만큼 시안 세그먼트가 새로 채워지는 것을 0.4 s 애니메이션으로 보여줍니다 — 위임에는 대가가 있다는 것을 숫자를 읽기 전에 느끼게 합니다.

## 12. 웨이브 경고 가독성

경고는 **소리를 끄고, 화면을 흘깃 보는** 사용자에게도 통해야 합니다. 사운드 없이 100% 전달되는 것이 요구사항입니다(모바일 기본 무음 가정).

### 12.1 타임라인

| 남은 시간 | 시각 | 청각 | 햅틱 |
|---|---|---|---|
| **T−20 s** | 상태 리본 웨이브 타이머가 앰버로 전환 + 원경 물색이 아주 서서히 붉게 편향(채도 +8%) | 앰비언스에 저역 드론 페이드인 | — |
| **T−12 s** | 위협이 올 **통로 입구**에 앰버 셰브런 3개가 진입 방향으로 흐름(0.8 s 주기) | 소나 핑 1회 | — |
| **T−6 s** | 화면 가장자리 해당 방향에 앰버 그라디언트 밴드가 0.8 s 주기로 맥동. 위협 나침반(E) 등장 | 소나 핑 2회 (간격 단축) | — |
| **T−3 s** | 카운트다운 숫자 3·2·1이 통로 입구 위에 크게(48 px) 표시, 매 초 스케일 팝 | 틱 3회 | 3에서 12 ms |
| **T−0** | 진입 지점에 레드 임팩트 링 + 짧은 화면 흔들림(4 px, 150 ms) | 임팩트 | 20 ms |
| **위협 처치 중** | 남은 적 수가 통로 입구 배지로 표시(숫자 + 도트) | — | — |
| **웨이브 종료** | 통로 색이 레드→시안으로 1.2 s 복귀, 보상 아이콘이 기지로 빨려 들어감 | 해제 코드(장3화음) | — |

### 12.2 판독 규칙

- 경고는 **항상 방향을 포함**합니다. "웨이브 3 시작" 같은 방향 없는 알림은 쓰지 않습니다.
- 동시 다발 웨이브: 통로별로 독립 표시. 3방향을 넘으면 화면 상단에 **미니 방향 다이얼**(반경 40 px)로 통합.
- 위협 강도는 **셰브런 개수(1~3) + 실루엣 크기**로 표현. 색 단계만으로 구분하지 않습니다.
- 보스급은 예고 시점부터 **화면 밖에서도 실루엣이 원경 레이어에 보입니다** (T−20 s부터 서서히 커짐).
- 플레이어가 다른 화면(연구/로그)을 보고 있으면 T−6 s에 **자동으로 월드로 복귀**하지 않고, 대신 해당 화면 상단에 축약 경고 바를 띄우고 탭하면 이동합니다(강제 화면 전환 금지).

## 13. 오디오 규칙

Web Audio 합성만 사용(외부 오디오 자산 없음). 기존 프로토타입의 합성 사운드 접근을 유지하되 **믹싱 구조**를 정의합니다.

### 13.1 버스 구조

| 버스 | 내용 | 기본 게인 |
|---|---|---|
| `ambience` | 심해 노이즈 패드, 수심별 필터 컷오프 | 0.22 |
| `base` | 기지 기계음 루프(전략별로 다름, §9) | 0.18 |
| `ui` | 탭, 확인, 오류 | 0.30 |
| `impact` | 전투, 폭발, 경고 | 0.35 |
| `reveal` | 해금 연출 전용 | 0.40 |

### 13.2 규칙

- **기본 음소거 상태로 시작**합니다(현재 `progression.ts`의 `sound:false`와 동일). 첫 실행 시 도크에 1회만 "소리 켜기" 힌트를 보여주고 다시 묻지 않습니다.
- 오디오 컨텍스트는 **첫 사용자 제스처에서만** 생성/재개합니다(자동재생 정책).
- **덕킹**: `reveal` 또는 `impact`가 울릴 때 `ambience`/`base`를 −6 dB, 220 ms 램프로 낮추고 400 ms에 복귀.
- **동시 발음 상한 16**, 같은 종류의 소리는 60 ms 안에 겹치면 병합(자원 수십 개 입고 시 소리 폭발 방지).
- 수심이 깊어지면 `ambience` 로우패스 컷오프를 2400 Hz → 600 Hz로 이동. 깊이를 귀로도 느끼게 합니다.
- 전략별 `base` 루프는 §9의 3종을 **동시에 믹스**하되 각 전략의 모듈 수 비율로 게인을 배분합니다. 기지를 들으면 어떤 기지인지 알 수 있습니다.
- 경고음은 **다른 어떤 소리와도 음색이 겹치지 않는 대역**(1.2 kHz 소나 핑)을 예약합니다.
- 모든 소리는 설정에서 버스 단위가 아니라 **한 개의 마스터 볼륨 + 음소거**로만 제어합니다(설정 과다 금지).

## 16. 기존 코드·문서와의 모순, 그리고 해결안

Round 1에서 발견한 실제 충돌입니다. 코드 수정은 하지 않았고, 각 항목에 구체 해결안을 붙였습니다.

### C1. `CLAUDE.md` 스택 표(Phaser 3) ↔ 이 문서(Canvas 2D)

`CLAUDE.md`는 런타임을 "Phaser 3 + Vite"로 확정 표기합니다. 그런데 현재 코드는 이미 **매 프레임 Canvas 2D로 그린 뒤 Phaser 텍스처에 반영**하는 구조이고(`README.md`의 "샘플의 범위" 절, `mobile-main.ts`의 `this.painter.render(run); this.surface.refresh()`), Phaser는 사실상 캔버스 표시용 껍데기입니다.

**해결안(권장)**: 신규 게임은 Phaser를 걷어내고 **Vite + TypeScript + 순수 Canvas 2D**로 갑니다.
- 근거: 매 프레임 캔버스 → GPU 텍스처 업로드가 이중 비용입니다. §6 예산(8 ms/frame)을 지키려면 이 업로드를 없애는 것이 가장 큰 단일 절감입니다. Phaser 엔진 1.21 MB도 그대로 사라집니다.
- 대신 §5.1의 오프스크린 레이어 캐시를 직접 관리합니다.
- **결정 권한은 코디네이터에게 있습니다.** Phaser 유지가 결정되면 §5.1 레이어를 Phaser 컨테이너/스프라이트로 1:1 매핑하고, 캔버스 전체 텍스처 갱신은 금지하는 것으로 대응 가능합니다(문서 수정 범위: §5.1, §6).
- 어느 쪽이든 `CLAUDE.md` 스택 표는 갱신이 필요하지만 **그 파일은 제 소유가 아니므로 손대지 않았습니다.**

### C2. `renderer.ts`의 텍스트 API가 아트 방향과 충돌

`MobileRenderer.text()`는 인자로 받은 `_color`를 **무시하고** 고정색 `#f4db9d`를 쓰며, 모든 라벨 뒤에 불투명 사각형(`#17373f`)을 강제로 깝니다(`src/mobile-renderer.ts:11-23`). 가독성 땜질이지만 화면이 "라벨 스티커 밭"이 되는 직접적 원인입니다.

**해결안**: 신규 렌더러의 텍스트는 ① 색 인자를 존중하고, ② 배경 박스 대신 **1px 어두운 아웃라인(`strokeText`) + 미세 드롭 오프셋**으로 대비를 확보합니다. 배경 박스는 HUD 패널 안에서만 씁니다.

### C3. 논리 해상도 고정 ↔ 반응형 요구

`MobileRenderer`는 420×460 논리 좌표에 하드코딩된 슬롯 좌표(`portraitSlots`, `portraitRoad`)를 씁니다. 화면 크기가 달라지면 비율이 깨지고, 최소 폭 360 px에서 여백이 남습니다.

**해결안**: 월드는 **월드 좌표 + 카메라(팬/줌)** 로 다루고, 화면 크기는 카메라 뷰포트 크기로만 반영합니다. 슬롯 좌표를 화면 좌표로 박지 않습니다. HUD만 CSS 픽셀 기준 레이아웃(§7)을 씁니다.

### C4. `AGENTS.md`의 "기존 게임 보존" ↔ 아비스 다이버 교체

`AGENTS.md`는 "이전 게임을 Git 히스토리에 보존"하라고 하고, 현재 `/`는 아비스 다이버 v2입니다. 신규 게임이 `/`를 차지하면 기존 엔트리와 충돌합니다.

**해결안**: 신규 게임을 **새 엔트리(`outpost.html`)** 로 추가하고, 완성·검증 후에 라우팅을 교체합니다. 기존 `index.html` / `showroom.html` / `challenge.html`은 그대로 남깁니다. 라우팅 최종 결정은 코디네이터 소관입니다.

### C5. 사운드 기본 꺼짐 ↔ 오디오로 정보 전달

`progression.ts`의 기본값은 `sound:false`입니다. 웨이브 경고를 소리에 의존하면 대다수 사용자가 정보를 놓칩니다.

**해결안**: §12를 "무음에서 100% 전달, 소리는 강화 채널"로 설계했습니다. 이 원칙을 후속 라운드에서도 유지해야 합니다. 오디오는 정보의 **중복**이지 유일 경로가 아닙니다.

### C6. `README.md`의 "게임 장면 = 매 프레임 캔버스 재그리기" 서술

README가 이미 "대규모 객체가 필요한 출시 버전에서는 개별 스프라이트·배칭으로 옮겨 최적화할 수 있습니다"라고 한계를 인정하고 있습니다. 신규 게임은 후반 모듈 30개+ 규모(§10.1)를 목표로 하므로 **처음부터** §5.1 캐시 구조로 시작해야 합니다. 나중에 옮기는 계획은 세우지 않습니다.

## 18. 병렬 초안 두 건과의 정합 (아키텍처 · 게임디자인)

Round 1 중 병렬 작업자가 두 초안을 올렸습니다.

- `docs/outpost-architecture.md` — 14열×20행 타일 그리드, 정수 Dijkstra 흐름장(벽 = 통행 비용), 순수 TS Sim + Canvas 2D 렌더러 + DOM HUD, **Phaser 미사용**, 코어 위 / 분출구 아래
- `docs/outpost-game-design.md` — 9열×14행, BFS 흐름장(**완전 봉쇄 허용** + 벽 공격), **Phaser 3 사용**, 균열 위 / 코어 아래, 전략 A/B/C, 숙련 자동화 70%

**두 초안이 서로 어긋나는 항목이 있습니다**(Phaser, 방어 방향, 봉쇄 규칙). §18.1은 합의된 것, §18.2는 아키텍처와의 충돌, §18.3은 아키텍처 덕분에 좋아지는 것, §18.4는 게임디자인과의 정합, §18.5는 결정 요청입니다.
**두 파일 모두 제 소유가 아니므로 수정하지 않았고, 아래는 전부 제안입니다.**

### 18.1 이미 해결된 항목

- **§16-C1 (Phaser)**: 아키텍처 초안은 "이 엔트리는 Phaser를 쓰지 않습니다"로 저와 결론이 같습니다. 다만 **게임디자인 초안 §17.1·§17.2는 Phaser 유지**(`render.ts # Phaser 스프라이트 풀링 렌더`, `main.ts # Phaser Scene 조립`)로 정반대입니다. → **미해결, 2:1.** §18.4-Y1에서 다룹니다.
- **§16-C4 (엔트리 분리)**: 아키텍처가 `outpost.html` 신규 엔트리를 잡았습니다. 기존 게임 보존과 충돌 없음. → **합의됨.**
- **§15-A1 (지형 모델)**: "통로 그래프" 가정은 **폐기**하고 타일 그리드 + 흐름장을 채택합니다. §8.3의 통로 시각화는 아래 18.3-b로 대체합니다(오히려 더 좋아집니다).
- **§15-A5 (세로 우선)**: 코어(행 1) ↔ 분출구(행 19)의 **세로 축 긴장**이 세로 화면과 정확히 맞습니다. 유지.

### 18.2 반드시 해결해야 할 충돌

**X1. 그리드 크기가 세 문서에서 전부 다르고, 그중 하나는 이 문서의 최대 금지 항목("작은 격자")에 정면으로 걸립니다.**

| 출처 | 그리드 | 390 px 폭 기준 타일 | 스크롤 |
|---|---|---|---|
| 아키텍처 초안 | 14열 × 20행 (280타일) | ≈ 25.7 px (360 px 기준) | 명시 없음 |
| 게임디자인 초안 | 9열 × 14행 (126타일) | ≈ 37~43 px | **없음. 전장이 한 화면** |
| 이 문서 초안(§7.4) | — | 모듈 64 px / 탭 48 px 요구 | — |
| **코디네이터 확정** | **9열 × 12행 (108타일)** | **≈ 40 px** | **없음 (맵 필수 패닝 금지)** | 

25.7 px는 §7.4 최소 탭 타깃 48 px의 절반 수준이고 일반 모바일 접근성 기준(44~48 px) 아래입니다. 이대로면 오탭이 일상이 되고 화면이 스프레드시트로 보입니다.

**해결 — 코디네이터가 9×12 / 40 px / 패닝 없음으로 확정했습니다. 이 문서는 그에 맞춥니다.**

1. **9×12 채택.** `tile = min(vw/9, vh*0.64/12)`. 390×844에서 min(43.3, 45.0) ≈ **43 px**, 360×640에서 min(40.0, 34.1) ≈ **34 px**. 즉 **작은 기기에서는 세로가 병목**입니다.
2. **타일 하한 40 px 규격.** 미달 시 열 수를 줄이지 말고 **월드 뷰포트 비율을 0.64 → 0.72까지 올려** 흡수합니다(360×640에서 0.72면 38.4 px). 그래도 미달인 초소형 기기(<340 px)에서만 마지막 수단으로 핀치 확대 1.0~1.6×를 엽니다. 12행으로 줄어든 덕에 14행일 때보다 하한을 지키기 쉬워졌습니다.
3. **작은 기기에서는 도크를 줄여 월드를 지킵니다.** 640 px 높이에서는 커맨드 도크 104 → 88 px, 컨텍스트 트레이 132 → 112 px로 축소하고, 월드는 절대 40 px 타일 아래로 내려가지 않게 우선순위를 둡니다.
4. **40 px 타일에서도 오조작이 없게 만드는 3중 장치**
   - **스냅 히트 테스트**: 탭 지점에서 화면 좌표 반경 24 px 내 최근접 *유효* 타일로 스냅(기존 `src/mobile-renderer.ts:input()`의 반경 스냅과 같은 발상). 타일이 붙어 있으므로 스냅은 항상 성공합니다.
   - **확정 행동은 전부 화면 좌표 56 px**: §8.2 건설 링 슬롯, 업그레이드/판매 버튼은 타일 크기와 무관하게 56 px입니다. **작은 것을 누르는 순간은 "선택"뿐이고 "확정"은 항상 크다** — 이 원칙 하나로 37 px 타일이 안전해집니다.
   - **2단 확정**: 링에서 손가락을 떼면 고스트가 놓이고, 확정은 56 px 버튼으로 받습니다(§8.2 개정). 작은 타일을 정확히 누를 필요가 없습니다.
5. **카메라 팬·2단 줌을 쓰지 않으므로** §7.1의 **F 카메라 홈은 삭제**하고, 그 자리에 §8.4 잠수정 액션을 둡니다. 화면 좌측 빈 물을 눌러 조이스틱을 만드는 게임디자인 §5 방식과도 충돌하지 않게 됩니다(팬 제스처가 없으므로).
6. **§8.1 제스처 사전 개정**: `드래그(빈 곳) = 카메라 팬` 항목을 **삭제**하고 `좌측 빈 물 홀드 = 잠수정 조이스틱`으로 교체합니다. `핀치`는 접근성 확대 전용으로 격하합니다.

*(참고: 14×20을 되살릴 경우에만 2단 줌 — 지휘 줌 56~64 px / 전략 줌 전체 보기, 전략 줌에서 타일 조작 비활성 — 이 필요하며, 그때는 좌측 홀드 조이스틱을 도크 버튼 홀드로 되돌려야 합니다. 현재 확정안에서는 불필요합니다.)*

**X2. 경고에 "방향"이 없으면 3개 분출구를 구분할 수 없습니다.**
바이옴 1은 분출구가 (1,19)·(7,19)·(12,19) 3곳입니다. §12.2는 "경고는 항상 방향을 포함한다"를 요구하는데, 현재 이벤트 `waveStart`는 `index`만 가지고 있고 T−20/12/6/3 예고에 쓸 신호가 없습니다.

**해결안 — 뷰에 예고 필드 추가 (이벤트가 아니라 뷰로)**
```ts
readonly waveCountdown: number;            // 다음 웨이브까지 초. 없으면 -1
readonly waveIncoming: readonly {          // 분출구별 예고 (길이 = 분출구 수)
  readonly vent: TileIndex;
  readonly strength: 0 | 1 | 2 | 3;        // 0=없음. §12.2 셰브런 개수와 1:1
}[];
```
예고는 매 프레임 필요하므로 1회성 이벤트가 아니라 **뷰 필드**여야 합니다. 이 3줄이면 §12 타임라인 전체가 구현 가능합니다. `callWave`로 플레이어가 직접 부른 경우에는 호출 시점부터 카운트다운이 시작되고 동일 타임라인을 씁니다.

**X3. 해금 연출 중 게임 시간 정지 (§11) — `SimCommand`에 정지 수단이 없습니다.**
**해결안**: Sim 계약을 건드리지 말고 **셸에서 해결**합니다. `ui/index.ts`의 rAF 루프가 연출 4.2 s 동안 `sim.step()` 호출을 멈추면 됩니다. 고정 스텝이므로 결정성이 깨지지 않습니다(스텝 수가 잠시 늘지 않을 뿐). §8.1의 2배속 토글도 같은 방식(프레임당 `step()` 2회)으로 계약 변경 없이 됩니다. 단 **"누적 시간이 아니라 스텝 수로 시뮬레이션한다"** 는 점을 셸 구현자가 지켜야 합니다.

**X4. `discovered` / `unlocked` 이벤트에 위치가 없습니다.**
§11 연출은 카메라를 대상 지점으로 옮기는 것이 1~2번째 비트입니다. **해결안**: 두 이벤트에 `at?: Vec2`를 추가하거나, 없으면 렌더러가 **코어 위치로 폴백**합니다. 폴백 규칙을 계약에 명시해 주면 이벤트 변경 없이도 진행 가능합니다.

**X5. 자동화 승격(§10.2) 신호가 없습니다.**
`setAutomation`은 명령만 있고, "이제 이 작업을 자동화할 수 있다"는 알림이 없습니다. **해결안**: 뷰에 `automationUnlocked: readonly AutomationKey[]`(현재 열려 있는 키 목록) 한 줄을 추가하면, 셸이 이전 프레임과 비교해 새로 늘어난 키에 §10.2의 배지·모프 연출을 붙일 수 있습니다.

**X6. 팔레트가 Canvas(TS)와 HUD(DOM/CSS) 두 곳에서 쓰입니다.**
**해결안**: `render/palette.ts` 하나를 유일한 출처로 두고, 부팅 시 그 객체를 순회해 `document.documentElement.style.setProperty('--c-'+key, hex)`로 CSS 변수를 주입합니다. CSS에 hex를 따로 적지 않습니다. 색 값이 두 곳에서 갈라지는 사고를 원천 차단합니다.

**X7. "렌더러는 상태 보유 금지(카메라 제외)" ↔ §5.1 레이어 캐시**
§5.1은 렌더러가 오프스크린 캔버스를 캐시하도록 요구합니다. **해결안**: 규칙을 "렌더러는 **게임 상태**를 보유하지 않는다"로 읽습니다. 카메라·레이어 캐시·라벨 폭 캐시 같은 **파생 렌더 캐시는 허용**되며, 원본은 언제나 뷰입니다. 문구를 그렇게 다듬어 주기를 제안합니다.

### 18.3 아키텍처 덕분에 오히려 좋아지는 것

- **a. 흐름장 = 공짜 경로 시각화.** 정수 Dijkstra 흐름장이 이미 타일마다 방향을 갖고 있으므로, §8.3의 "막으면 어디로 도나"를 **별도 계산 없이** 그릴 수 있습니다. 벽 고스트를 올린 상태의 임시 흐름장을 한 번 더 계산해 **차분이 생긴 타일만** 점선 화살표로 애니메이션하면 됩니다.
- **b. 통로 색 표현 대체안.** §8.3의 "통로가 붉게 물든다"는 타일 그리드에서 **적이 실제로 지나갈 흐름장 경로 타일에 그라디언트 트레일**을 그리는 것으로 구현합니다. 원래 안보다 정확합니다(적이 안 오는 길은 물들지 않음).
- **c. 벽을 "비용"으로 취급하는 결정**은 §9.1 요새 전략의 "완전 봉쇄 불가" 시각 표현(부서진 육각 아이콘)과 정확히 맞습니다. 유지.
- **d. 뷰 객체 풀링 + `prev` 보간 필드**는 §5.5 애니메이션 문법(이징·오버슈트)을 프레임당 할당 0으로 구현하게 해줍니다. §6 예산에 유리합니다.
- **e. 잔해(경제)를 바깥 레인에만 배치**한 결정 덕분에 §9.2 산업 전략의 "도관이 위험한 바깥으로 뻗는다"가 레이아웃 차원에서 자동으로 성립합니다.

### 18.4 게임디자인 초안(`docs/outpost-game-design.md`)과의 정합

같은 라운드에 게임디자인 초안도 올라왔습니다. **아키텍처 초안과 게임디자인 초안이 서로 어긋나는 지점**이 있어 함께 정리합니다.

**Y1. Phaser — 세 문서가 2:1로 갈립니다. (최우선 결정)**
아키텍처 §0은 "Phaser를 쓰지 않습니다", 이 문서 §16-C1도 제거 권장인데, 게임디자인 §17.1은 "Phaser 3 + Vite"를 제약으로 두고 §17.2 파일 구조에 `render.ts # Phaser 스프라이트 풀링 렌더`, `main.ts # Phaser Scene 조립`을 명시했습니다.
**권장: Phaser 제거.** 아트 관점의 근거를 덧붙이면, §5.1의 L0~L10 레이어와 §5.2 3단 셰이딩·§5.3 다중 알파 블룸은 **캔버스 합성(`globalCompositeOperation`, 오프스크린 캐시) 위에서 성립**하는 기법입니다. Phaser 스프라이트 풀링으로 가면 이 기법들을 텍스처로 미리 구워야 하고, 티어별 실루엣 변화(§5.4)나 전력 케이블 같은 **동적 벡터 요소**를 스프라이트로 표현하기 어려워집니다. 게임디자인 §9가 원하는 "전력 케이블이 실제로 그려진다 / 조명 반경이 넓어진다"도 캔버스 벡터 쪽이 훨씬 자연스럽습니다.

**Y2. 방어 방향이 반대입니다.**
아키텍처는 코어가 **위**(행 1), 분출구가 **아래**(행 19). 게임디자인은 균열이 **위**, 코어가 **아래**.
**권장: 게임디자인 쪽(코어 아래 / 위협 위).** 아트 근거 3가지 —
1. 기지 실루엣이 화면 **하단에 쌓이며 위로 자랍니다.** 성장이 "차오르는" 것으로 읽혀 §3 필러 4에 맞습니다. 코어가 위면 기지가 화면 위쪽에 매달린 모양이 됩니다.
2. 위협이 **어두운 위쪽에서 내려옵니다.** §4.3 대기 원근에서 먼 곳(원경)을 어둡게 처리하므로, 위협이 어둠에서 서서히 드러나는 §12 T−20 s 실루엣 예고가 자연스럽게 성립합니다.
3. 플레이어가 가장 많이 만지는 기지가 **엄지 근처(하단)** 에 옵니다. §14 한손 조작 규칙과 일치합니다.

**Y3. 완전 봉쇄 허용 여부가 반대입니다.**
아키텍처는 벽을 통행 **비용**으로 처리(완전 봉쇄 불가), 게임디자인은 완전 봉쇄를 **허용**하되 경로가 없으면 최근접 벽을 공격.
아트 관점에서는 **둘 다 그릴 수 있지만 그리는 것이 다릅니다.**
- 비용 모델 채택 시: §8.3의 "부서진 육각 아이콘"(봉쇄 불가 지점 표시)과 흐름장 차분 점선(§18.3-a)을 씁니다.
- 봉쇄 허용 모델 채택 시: 고스트가 완전 봉쇄를 만드는 순간 **미리보기가 바뀝니다** — 새 경로 점선 대신 그 벽 위에 `threat.red` 조준 레티클과 "여기를 때립니다" 아이콘이 뜨고, 예상 피격 벽이 맥동합니다. 플레이어가 봉쇄의 결과를 **짓기 전에** 봅니다.
**권장: 게임디자인 쪽(봉쇄 허용 + 벽 공격).** 미리보기가 더 극적이고, "내가 만든 벽이 표적이 된다"는 것이 방어 게임의 감정에 맞습니다. 어느 쪽이든 §8.3은 위 두 문장 중 하나를 고르면 됩니다.

**Y4. 게임디자인 §9의 시각화 항목을 레이어 스택에 정식 편입합니다.** (충돌 아님, 흡수)

| 게임디자인 §9 항목 | 편입 위치 |
|---|---|
| 전력 케이블(과부하 시 깜빡임) | **새 레이어 L4.5 «전력망»** — 배치 변경 시에만 캐시 갱신, 과부하 깜빡임만 매 프레임. 케이블은 §5.4 도관 문법(외피 `hull.lo` 4 px + 내부 흐름 2 px) 재사용, 과부하는 `alert.amber` 0.8 s 펄스 |
| 조명 반경 | L9 조명 합성 패스에 통합. 암흑 구역(§10.3 구역 5)에서는 **조명 밖을 알파 0.82 `ink.abyss`로 덮는 마스크** 1장으로 처리 — 이것이 곧 사거리 정보이므로 장식이 아니라 게임 정보 레이어입니다 |
| 깊이 안개(위 청색 / 아래 주황) | §4.3 대기 원근 + L0 그라디언트로 이미 커버. Y2 채택 시 **위=차가움·아래=따뜻함**으로 방향을 확정합니다 |
| 실루엣 밀도(후반 화면 하단 1/3) | §10.1 "후반 모듈 30개+"의 구체 기준으로 채택 |
| 드론 궤적 = 위임한 양 | L6에서 드론마다 **잔상 트레일 6프레임**(알파 감쇠)을 그립니다. 자동화가 늘수록 화면의 시안 선이 늘어나 §10.2의 보상이 누적적으로 보입니다 |

**Y5. 자동화 70% 규칙 — 이 문서 §10.2를 개정했습니다.**
초안의 "자동화하면 수동 버튼이 사라진다"는 게임디자인 §6("자동화는 항상 원본보다 나쁘다")과 충돌합니다. §10.2를 **버튼이 사라지는 대신 `필요`→`선택` 상태로 바뀌고 드론 글리프가 공전하는** 연출로 고쳤습니다. 전력 소비 증가도 승격 순간에 보여줍니다.

**Y6. 잠수정 조작 — 이 문서 §8.4를 개정했습니다.**
게임디자인 §5의 "좌측 아무 곳이나 홀드 → 조이스틱 생성, 조준 자동, 코어 조각 12초 소멸"에 맞춰 §8.4를 모드 진입 방식에서 **상시 유닛 + 좌측 홀드 스틱**으로 고쳤고, 12초 소멸에 대한 판독 규칙(줄어드는 링, 3초부터 레드, 화면 밖 화살표)을 추가했습니다.

**Y7. 전략 3종 이름 — 이 문서 §9를 개정했습니다.** §9.4에 A/B/C 매핑 표를 넣고, 판독 키를 **면(A) / 바닥(B) / 선(C)** 으로 정리했습니다.

**Y8. 성능 예산이 다릅니다(충돌 아님, 병합 가능).**
게임디자인 §17.4는 시뮬 측(적 60 / 구조물 120 / 투사체 80 / 시뮬 3 ms), 이 문서 §6은 렌더 측(8 ms, 900 draw ops, 파티클 180)입니다. 합치면 **시뮬 3 ms + 렌더 8 ms = 11 ms < 16.6 ms**로 60 fps 예산 안에 들어옵니다. 다만 게임디자인의 "저사양 45 fps 하한"과 §6의 "22 ms 초과 시 품질 강등"은 같은 것을 다르게 말한 것이므로 **22 ms(≈45 fps) 기준으로 통일**할 것을 제안합니다.

**Y9. 게임디자인 §17.5 저장 시점에 아트 요구를 하나 더합니다.**
"앱 백그라운드 전환 시 저장"은 §6의 "백그라운드 진입 시 렌더 루프 정지"와 같은 훅에 걸립니다. 복귀 시에는 **레이어 캐시를 무효화하고 1프레임 안에 재구성**해야 흰 화면이나 깨진 프레임이 보이지 않습니다.
